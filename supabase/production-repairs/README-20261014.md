### Songwriting repair

Restores the API used by the existing frontend: `start_songwriting_polish_session`, `complete_songwriting_polish_session`, `skip_songwriting_polish`, `complete_songwriting_project`, `complete_songwriting_project_with_instruments`, and `skip_and_complete_songwriting_project_with_instruments`. Restores `auto_complete_songwriting_polish_sessions` for the already-deployed `cleanup-songwriting` Edge Function (cron interval 15 minutes).

The live schema already had 103 projects with `status='completed'`, each linked to at least one existing row in `songs` by `songwriting_project_id`, while every project had `song_id IS NULL`. Seven songwriting projects have more than one linked song. This repair deterministically adopts the oldest existing matching song and never regenerates an existing one. It does **not** automatically backfill historical projects, remove ambiguous duplicate songs, award XP or retroactively reroll older song quality. The newly restored completion wrapper prioritises existing song quality; it does **not** yet reimplement the historical advanced outcome calculator or historic instrument/clothing bonus pipelines. Two older completed projects had music or lyrics progress below 2000 and still need separate reconciliation.

**Verified with rollback-only database tests** on representative existing projects:
- An unauthorized account cannot skip polish for someone else's character.
- Keep-as-is links exactly one pre-existing song; a repeated call reports `duplicate=true`.
- One-hour polish can start, resolve after its due time, and finish by linking the canonical song.
- Each test forced an exception within a PL/pgSQL subtransaction and verified no permanent test writes.

UI browser testing is still required.

### Gig consequences repair

- Retains all **307** original `gig_post_processing` rows unchanged (**61** unique gigs; **246** duplicate attempts).
- Mirrors all rows into the protected `gig_post_processing_attempt_archive`; a zero-mismatch count check was successful.
- Creates `gig_post_processing_canonical` with one claim per ready completed gig (**59 pending**), separate from the legacy table.
- Adds `band_live_reputation`, `gig_media_reviews`, snapshot linkage, and service-role-only functions for bounded and idempotent processing, based on immutable outcome evidence.
- The processor **does not issue XP or fan awards**. It only observes those core rewards and computes the separate live-reputation consequence.
- Tested processing one claim (four evidence records) and a repeated call (`alreadyProcessed=true`) inside a rollback-only transaction.
- **Recurring gig-consequences cron is deliberately NOT enabled.** A subsequent attempt to run a live 5-gig processing batch was blocked. None of the 59 historical claims were processed; they remain `pending`.

The original `20261008193206_idempotent_gig_consequences.sql` still includes destructive duplicate deletions and must not be replayed without resolving issue #4040. This repair avoids that deletion, but the legacy game UI may still display older `processing` status because it reads the old table.

## Follow-up live repairs — guarded song bonuses and gig status visibility

Two further production changes were applied and retained as separate SQL in this folder:

| Recorded migration | SQL file |
| --- | --- |
| `rockmundo_20261014_songwriting_instrument_clothing_bonus_guarded` | `20261014140000_songwriting_instrument_clothing_bonus_guarded.sql` |
| `rockmundo_20261014_gig_canonical_status_band_read_only` | `20261014140100_gig_canonical_status_band_read_only.sql` |

**New songwriting completions only:** The original instrument migration could multiply an already-scaled instrument quality bonus by 10, producing excessive 1,000-quality songs. The replacement deduplicates instrument choices, resolves true character skill levels and equipped clothing on the server, caps the absolute instrument bonus to 150 quality points, caps clothing to 20%, and stores a transparent breakdown. It runs exactly once after canonical completion under the same transaction lock. Historical completed projects lack `completion_quality_breakdown.source='live_songwriting_quality'` and therefore keep their existing song scores. Verified using rollback-only tests for the legacy-preservation path, new-provenance bonus path, score cap, and repeat request idempotency. No historical song quality was mutated.

**Gig viewer:** The canonical per-gig processing state was not visible to the client, which instead showed stale `processing` rows from the legacy table. Production now grants *column-level read access only* to `gig_id`, `status`, `processing_version`, `completed_at`, under band-membership RLS; authenticated players cannot read the private `error_snapshot` or `audit_history` columns and cannot update processing rows. `GigExperienceService` now prefers the canonical status and falls back to legacy when the newer schema is unavailable. Corresponding loader tests cover canonical precedence and legacy compatibility.

**Do not enable the gig processor cron yet.** The 59 pending claims remain unprocessed. These SQL files are an exact record of changes already applied directly to production, and should not be replayed by automated database migration tooling.

## Completion inbox follow-up

The production repair also restores a future-only completion inbox signal, under two historical records:

- `rockmundo_20261014_songwriting_completion_inbox_once` (version `20261014134925`)
- `rockmundo_20261014_songwriting_completion_inbox_format_fix` (version `20261014135028`)

The **combined, corrected effective SQL** is retained at `20261014140500_songwriting_completion_inbox_once.sql`. The first applied function used a printf-style `%.1f` with PostgreSQL `format()`, which PostgreSQL does not support. The second migration corrected it to `%s` using `to_char()`. A production rollback-only test then successfully simulated one transition from writing to completed, verified one inbox notification and the stored writing-quality snapshot, replayed an unchanged completed status without a second notification, and proved all test writes rolled back.

The notification index prevents duplicate `source='songwriting_completion'` rows per project. It does **not** backfill or message the 103 previously completed projects. No real player inbox rows were created during the test. Do not replay these scripts on production through automatic migration tooling.

## Legacy completed songs with partial progress

The live database includes **2** historical songwriting projects with `status='completed'` but at least one progress counter below 2000. Both have a matching canonical song owned by the same account **and character**. They previously could not use the new review RPCs, and the project card treated them as still in progress.

Recorded as `rockmundo_20261014_completed_songwriting_legacy_progress_guard`, the SQL in `20261014141000_songwriting_completed_legacy_progress_guard.sql` now permits final-polish start, skip, and canonical completion for these projects **only when** an existing `songs` record matches project ID, account ID, and character ID. It does not adjust stored progress, create additional copies of a song, grant XP, or override its quality. A rollback-only test passed the keep-as-is completion, original song ID and score preservation, and duplicate retry checks.

`SimplifiedProjectCard.tsx` now considers an explicit `completed`/`converted` status or a linked song to be finished, even if stale progress counters are lower. This restores the completion review action and prevents re-starting writing sessions for already-finished songs. A regression test guards the UI condition.
