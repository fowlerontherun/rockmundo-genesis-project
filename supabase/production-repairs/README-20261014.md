### Songwriting repair

Restores the API used by the existing frontend: `start_songwriting_polish_session`, `complete_songwriting_polish_session`, `skip_songwriting_polish`, `complete_songwriting_project`, `complete_songwriting_project_with_instruments`, and `skip_and_complete_songwriting_project_with_instruments`. Restores `auto_complete_songwriting_polish_sessions` for the already-deployed `cleanup-songwriting` Edge Function (cron interval 15 minutes).

The live schema already had 103 projects with `status='completed'`, each linked to at least one existing row in `songs` by `songwriting_project_id`, while every project had `song_id IS NULL`. Seven songwriting projects have more than one linked song. This repair deterministically adopts the oldest existing matching song and never regenerates an existing one. It does **not** automatically backfill historical projects, remove ambiguous duplicate songs, award XP or retroactively reroll older song quality. The newly restored completion wrapper prioritises existing song quality; it does **not** yet reimplement the historical advanced outcome calculator or historic instrument/clothing bonus pipelines. Two older completed projects had music or lyrics progress below 2000 and still need separate reconciliation.

**Verified with rollback-only database tests** on representative existing projects:
- An unauthorized account cannot skip polish for someone else's character.
- Keep-as-is links exactly one pre-existing song; a repeated call reports `duplicate=true`.
- One-hour polish can start, resolve after its due time, and finish by linking the canonical song.
- Each test forced an exception within a PL/pgSQL subtransaction and verified no permanent test writes.

UI browser testing is still required.

### Gig consequences repair

- Retains all **307** original `gig_post_processing` rows unchanged (**61** unique gigs; **246** duplicate attempts).
- Mirrors all rows into the protected `gig_post_processing_attempt_archive`; a zero-mismatch count check was successful.
- Creates `gig_post_processing_canonical` with one claim per ready completed gig (**59 pending**), separate from the legacy table.
- Adds `band_live_reputation`, `gig_media_reviews`, snapshot linkage, and service-role-only functions for bounded and idempotent processing, based on immutable outcome evidence.
- The processor **does not issue XP or fan awards**. It only observes those core rewards and computes the separate live-reputation consequence.
- Tested processing one claim (four evidence records) and a repeated call (`alreadyProcessed=true`) inside a rollback-only transaction.
- **Recurring gig-consequences cron is deliberately NOT enabled.** A subsequent attempt to run a live 5-gig processing batch was blocked. None of the 59 historical claims were processed; they remain `pending`.

The original `20261008193206_idempotent_gig_consequences.sql` still includes destructive duplicate deletions and must not be replayed without resolving issue #4040. This repair avoids that deletion, but the legacy game UI may still display older `processing` status because it reads the old table.
